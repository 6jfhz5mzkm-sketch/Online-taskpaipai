## 一、项目立项说明

### 1.1 核心定义

**商家任务体系**是面向京东拍拍二手平台POP商家的引导型运营系统，通过结构化的任务清单，覆盖商家从入驻准备（含模式认知、资质准备、申请入驻、审核跟进、开店设置）到基础运营、营销投放、数据分析的全生命周期经营路径。

系统以H5页面为核心载体，飞书消息推送为辅助触达手段，帮助商家在正确的路径上高效经营，降低平台运营人力成本，提升商家入驻后的经营效率和生命周期价值。

### 1.2 目标受众

| 角色 | 说明 |
|------|------|
| **核心用户** | 拍拍二手POP模式企业商家（约2000家，活跃约200家） |
| **运营者** | 平台运营人员，负责任务配置、商家筛选、优惠券发放 |
| **管理者** | 产品/业务负责人，关注整体数据和商家成长 |

### 1.3 项目背景

拍拍二手平台目前面临以下现状：

- 商家以企业类型为主，规模差异大，运营能力参差不齐
- 入驻环节有人工引导，流失可控，但**入驻后的经营阶段流失严重**
- 商家普遍不具备规模化起量能力，传统方式破单慢
- 平台免费流量逐渐萎缩，转向付费模式
- 缺乏系统化的商家成长引导机制

## 二、解决痛点问题

### 2.1 商家侧痛点

| 痛点 | 具体表现 | 任务体系如何解决 |
|------|---------|-----------------|
| 不知道怎么做 | 入驻后缺乏经营指引，不知道从哪开始 | 结构化任务清单，明确每一步该做什么 |
| 执行门槛高 | 知道要做但不知道怎么做 | 提供模板、案例、工具，降低执行难度 |
| 没有节奏感 | 经营动作零散，缺乏系统性 | 阶段化任务设计，帮商家建立经营节奏 |
| 破单困难 | 传统方式引流慢，首单周期长 | 针对性引导优化商品呈现、定价、服务 |

### 2.2 平台侧痛点

| 痛点 | 具体表现 | 任务体系如何解决 |
|------|---------|-----------------|
| 运营人力成本高 | 人工逐个引导商家，不可规模化 | 任务体系自动化引导，降低人力依赖 |
| 商家流失难挽回 | 商家经营一段时间后离开平台 | 任务体系持续触达，延长商家生命周期 |
| 商家能力难评估 | 无法量化商家的经营能力和成长潜力 | 任务完成度作为商家能力评估依据 |
| 优质商家难识别 | 不知道哪些商家值得重点扶持 | 通过任务数据筛选优质商家，精准发放优惠券 |

## 四、第一版核心目标

### 4.1 核心目标

**通过入驻准备阶段的5个一级任务（模式选择与认知、资质材料准备、申请入驻、审核跟进、开店设置），让商家对任务体系建立认知和使用习惯，同时为后续经营阶段的任务打下数据基础。**

### 4.2 量化指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 入驻任务完成率 | ≥ 70% | 完成阶段一+阶段二所有必做任务的商家比例 |
| 任务中心访问率 | ≥ 80% | 入驻期间至少访问1次任务中心的商家比例 |
| 飞书绑定率 | ≥ 60% | 完成飞书账号绑定的商家比例 |
| 数据采集完成率 | ≥ 90% | 品类选择、退货地址等基础数据完整度 |
| 首单完成率 | ≥ 30% | 入驻后7天内完成首单的商家比例 |

### 4.3 V1不做的事

- 不做经营阶段的周期性任务
- 不做营销投放相关任务
- 不做数据分析看板
- 不做复杂的游戏化机制（积分、徽章、等级）
- 不做商家排名/榜单
- 不做AI自动生成任务
- 不做第三方任务接入
- **不做AI智能客服**（V2+ 规划，V1 阶段预留接口）

## 六、产品流程和用户路径

### 6.1 整体流程

```
商家注册 → 实名认证 → 绑定飞书 → 选择品类 → 设置售后 → 绑定结算 → 上架商品 → 首单完成
    │         │          │          │          │          │          │          │
    ▼         ▼          ▼          ▼          ▼          ▼          ▼          ▼
  任务1     任务2       任务3       任务4       任务5       任务6       任务7       任务8
```

### 6.2 用户路径

#### 路径一：入驻引导路径（主路径）

```
1. 商家完成注册
2. 跳转任务中心H5页面
3. 看到入驻进度（0%）
4. 按顺序完成必做任务
5. 每完成一个任务，进度条推进
6. 完成阶段一所有任务，获得阶段完成祝贺
7. 继续完成阶段二任务
8. 完成阶段二，入驻流程结束
9. 进入经营阶段（V2+）
```

#### 路径二：飞书触达路径

```
1. 商家绑定飞书账号
2. 系统根据任务进度推送飞书消息
3. 商家点击飞书卡片中的"查看任务"
4. 跳转H5任务中心
5. 继续完成待完成任务
```

#### 路径三：日常访问路径

```
1. 商家通过商家后台链接进入任务中心
2. 查看当前进度和待完成任务
3. 完成任务或查看引导内容
4. 退出任务中心
```

## 七、数据和业务对象

### 7.1 核心业务对象

| 对象 | 说明 | 关键属性 |
|------|------|---------|
| **商家（Merchant）** | 拍拍POP商家 | merchant_id, name, category, status, feishu_id |
| **任务（Task）** | 系统配置的任务 | task_id, name, stage, type, completion_type, status |
| **任务进度（TaskProgress）** | 商家的任务完成记录 | merchant_id, task_id, status, completed_at |
| **阶段（Stage）** | 任务所属阶段 | stage_id, name, sort_order, description |
| **推送记录（PushLog）** | 飞书推送记录 | merchant_id, template_type, sent_at, opened_at |

### 7.2 数据采集点

| 数据类型 | 采集内容 | 用途 |
|---------|---------|------|
| 商家基础数据 | 品类、规模、活跃度 | 标签体系，V2推荐基础 |
| 任务行为数据 | 访问、点击、完成、耗时 | 任务效果分析 |
| 触达效果数据 | 推送送达、打开、点击 | 推送策略优化 |
| 经营数据（预留） | 上架量、回复率、发货时效 | V2运营任务触发 |

### 7.3 数据表结构

```sql
-- 商家表
CREATE TABLE merchant (
    merchant_id     VARCHAR(32) PRIMARY KEY,
    name            VARCHAR(100),
    category        VARCHAR(50),
    status          ENUM('onboarding','active','inactive'),
    feishu_id       VARCHAR(50),
    created_at      TIMESTAMP,
    updated_at      TIMESTAMP
);

-- 任务配置表
CREATE TABLE task_config (
    task_id         VARCHAR(32) PRIMARY KEY,
    stage           ENUM('onboarding','setup','operation','marketing','analytics'),
    task_name       VARCHAR(100),
    task_type       ENUM('mandatory','suggested','guide'),
    completion_type ENUM('system_check','manual_submit','click_read'),
    sort_order      INT,
    status          ENUM('active','inactive'),
    created_at      TIMESTAMP,
    updated_at      TIMESTAMP
);

-- 商家任务进度表
CREATE TABLE merchant_task_progress (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    merchant_id     VARCHAR(32),
    task_id         VARCHAR(32),
    status          ENUM('pending','in_progress','completed','expired'),
    completed_at    TIMESTAMP,
    created_at      TIMESTAMP
);

-- 推送记录表
CREATE TABLE push_log (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    merchant_id     VARCHAR(32),
    template_type   VARCHAR(50),
    sent_at         TIMESTAMP,
    opened_at       TIMESTAMP,
    clicked_at      TIMESTAMP
);
```

├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────────────┐    ┌─────────────────┐            │
│  │  H5 任务中心     │    │  PC 管理后台     │            │
│  │  (商家端)        │    │  (运营端)        │            │
│  │  移动端优先       │    │  桌面端           │            │
│  └────────┬────────┘    └────────┬────────┘            │
│           │                      │                      │
│           └──────────┬───────────┘                      │
│                      ▼                                  │
│           ┌─────────────────────┐                       │

### 8.2 唯一推荐技术栈

#### 总览

| 层级 | 技术方案 | 版本 |
|------|---------|------|
| **H5前端** | uni-app + Vue 3 + Vite + uview-plus + Pinia + TypeScript（2026-08 决策变更，原 Vant 4） | Vue 3.4+ / uni-app 3.x |
| **管理后台** | Vue 3 + Vite + Element Plus + Pinia + TypeScript | Vue 3.4+ |
| **后端服务** | Python 3.12 + FastAPI + SQLAlchemy 2.0 + Pydantic v2（2026-09 由 NestJS 迁移完成） | Python 3.12 |
| **数据库** | MySQL 8.0 | 8.0 |
| **缓存** | 当前未使用（api-py 无 Redis 依赖） | - |
| **部署** | Nginx + uvicorn（systemd 守护） | - |
| **飞书对接** | 飞书开放平台 HTTP API（httpx 直连 OAuth） | - |

#### 前端技术栈详解

**H5任务中心（商家端）**

| 技术 | 作用 | 选型理由 |
|------|------|---------|
| Vue 3 | 前端框架 | Composition API简洁，国内生态最成熟 |
| Vite | 构建工具 | 构建速度快，热更新快，开发体验好 |
| uview-plus | UI组件库 | uni-app 生态移动端组件库（2026-08 决策变更，原 Vant 4）；Token 与组件规范见 `project/docs/设计规范.md` |
| Pinia | 状态管理 | Vue 3官方推荐，轻量级，TypeScript支持好 |
| TypeScript | 类型系统 | 前后端同语言，类型定义可复用 |
| Vue Router | 路由管理 | Vue 3官方路由，与Vue 3深度集成 |

**管理后台（运营端）**

| 技术 | 作用 | 选型理由 |
|------|------|---------|
| Vue 3 | 前端框架 | 与H5端统一技术栈，降低维护成本 |
| Vite | 构建工具 | 同上 |
| Element Plus | UI组件库 | PC端最成熟的Vue 3组件库，表格/表单组件丰富 |
| Pinia | 状态管理 | 同上 |
| TypeScript | 类型系统 | 同上 |

#### 后端技术栈详解

| 技术 | 作用 | 选型理由 |
|------|------|---------|
| Node.js | 运行时 | 异步非阻塞，适合IO密集型业务；飞书SDK原生支持 |
| NestJS | 后端框架 | 模块化架构，依赖注入，企业级最佳实践 |
| TypeORM | ORM框架 | TypeScript原生支持，与NestJS深度集成 |
| TypeScript | 类型系统 | 前后端同语言，共享类型定义 |
| class-validator | 数据校验 | NestJS生态，声明式校验 |
| class-transformer | 数据转换 | 对象序列化/反序列化 |

#### 数据层详解

| 技术 | 作用 | 选型理由 |
|------|------|---------|
| MySQL 8.0 | 主数据库 | 最成熟的关系型数据库，商家数据结构清晰 |
| Redis 7 | 缓存 | 任务状态缓存、防重复提交、会话管理 |

#### 部署和运维

| 技术 | 作用 | 选型理由 |
|------|------|---------|
| Nginx | 反向代理 + 静态资源 | H5页面CDN加速，API转发 |
| PM2 | Node.js进程管理 | 自动重启、负载均衡、日志管理 |
| Docker（可选） | 容器化 | 简化部署环境配置 |

### 8.3 为什么选择这套技术栈

#### 核心理由

| 理由 | 说明 |
|------|------|
| **全栈TypeScript** | 前后端同语言，类型定义可复用，降低沟通和维护成本 |
| **Vue 3生态成熟** | 国内社区活跃，文档完善，遇到问题容易找到解决方案 |
| **NestJS企业级** | 结构化好、模块化清晰，适合业务系统，不像Express那样太自由 |
| **Vant 4移动端** | 专为移动端H5设计，组件丰富，开箱即用 |
| **轻量级部署** | Node.js服务 + 静态资源，不需要复杂的运维 |
| **快速迭代** | Vite构建快、热更新快，4-6周可交付V1 |

#### 与项目需求的匹配度

| 项目需求 | 技术栈如何满足 |
|---------|---------------|
| H5移动端任务中心 | Vue 3 + Vant 4，移动端组件开箱即用 |
| 任务状态管理 | Pinia状态管理 + NestJS模块化服务 |
| 飞书消息推送 | Node.js生态对HTTP API对接友好，飞书SDK原生支持 |
| 任务配置后台 | Vue 3 + Element Plus，PC端管理界面成熟方案 |
| 快速迭代（4-6周） | Vite构建快、NestJS开发效率高 |
| 数据埋点 | 前端埋点SDK + 后端数据采集接口 |
| 轻量级部署 | Nginx + PM2，单机可承载200商家并发 |

### 8.4 其他技术栈不选择的理由

#### 前端框架对比

| 技术栈 | 不选择的理由 |
|--------|-------------|
| **React** | 国内Vue生态更成熟；Vant是Vue专属；团队如果熟悉Vue，切换成本高 |
| **Angular** | 太重，学习曲线陡峭；对于2-3人小团队，开发效率不如Vue |
| **原生JS/jQuery** | 不具备工程化能力，后期维护困难 |
| ~~Taro/uni-app~~ | **【2026-08 决策变更】原结论为「本项目是 H5 不是小程序，不需要跨端框架」；现决策：采用 uni-app**（一套代码覆盖 PC Web + 移动端 H5，并为后续多端能力预留）。真源：`project/docs/设计规范.md`、`project/docs/开发规则.md` |

#### 后端框架对比

| 技术栈 | 不选择的理由 |
|--------|-------------|
| **Spring Boot (Java)** | 太重，启动慢，200商家的系统不需要Java的重量级方案；团队学习成本高 |
| **Express/Koa** | 太自由，没有约束，业务复杂后代码容易混乱；不适合业务系统 |
| **Gin (Go)** | Go生态国内不如Node.js成熟；飞书SDK支持不如Node.js |
| **Django/FastAPI (Python)** | Python性能不如Node.js；异步处理不如NestJS优雅 |

#### 数据库对比

| 技术栈 | 不选择的理由 |
|--------|-------------|
| **PostgreSQL** | 功能比MySQL强大，但对于本项目杀鸡用牛刀；MySQL更简单 |
| **MongoDB** | 任务数据是结构化关系型数据，不需要NoSQL |
| **SQLite** | 不适合生产环境，不支持并发 |

### 8.5 技术栈适用边界

#### 当前技术栈完美适用的场景

| 场景 | 说明 |
|------|------|
| 商家规模 ≤ 5000家 | 单机Node.js + MySQL可轻松承载 |
| 日活 ≤ 500 | 无并发压力 |
| 业务逻辑中等复杂度 | NestJS模块化可良好组织 |
| 团队规模 2-5人 | TypeScript统一技术栈，协作高效 |
| 迭代周期 4-8周/版本 | 快速迭代，Vite + NestJS开发效率高 |

#### 什么情况下需要重新评估技术路线

| 触发条件 | 当前技术栈的瓶颈 | 建议调整 |
|---------|-----------------|---------|
| **商家规模 > 10000家** | Node.js单线程可能成为瓶颈 | 热点服务迁移到Go/Java |
| **日活 > 2000** | 需要考虑水平扩展 | 引入负载均衡 + 数据库读写分离 |
| **业务逻辑极度复杂** | NestJS模块化可能不够 | 评估是否需要微服务拆分 |
| **团队 > 10人** | 前后端协作成本增加 | 考虑BFF层或GraphQL |
| **需要实时通信** | 当前架构不支持WebSocket | 引入WebSocket服务 |
| **需要复杂数据分析** | MySQL分析查询性能有限 | 引入ClickHouse/Elasticsearch |
| **需要AI/ML能力** | Node.js不适合 | Python服务独立部署 |

### 8.6.1 AI 能力预留（V2+）

项目后续计划在前端挂载智能客服能力，为商家提供实时答疑和经营建议。

**技术方案：**
- 调用外部大模型 API（OpenAI / 通义千问 / DeepSeek 等），不自建模型
- Node.js 对所有主流 LLM 均有官方 SDK 支持，无技术瓶颈
- V1 阶段在后端预留 `ai/` 模块目录，V2 接入时零架构改动

**后端模块预留结构：**
```
src/modules/ai/
├── ai.module.ts           # AI 模块定义
├── chat.controller.ts     # 对话接口
├── chat.service.ts        # 调用 LLM API
├── rag.service.ts         # 检索业务知识（任务文档、FAQ）
└── conversation.entity.ts # 对话历史存储
```

**V2 接入工作量：** 安装 LLM SDK + 写 ChatService + 前端对话组件，约 1-2 周。
