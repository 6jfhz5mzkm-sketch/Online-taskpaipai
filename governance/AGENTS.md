# Agent 工作守则（项目根宪法）

> 本文件是 AI Agent 在本项目中的**最高行为准则**。项目根 = `Task Framework/`（git 根）。
> 运行语言：简体中文；所有标识符（文件/目录/变量/函数/类/常量等）一律英文命名（全局规则，见 `dev-docs/铁律.md` 铁律 4）。
> 总控/子 Agent 协作细则由 `dev-docs/铁律.md`、`dev-docs/Agent协作体系.md` 承载；本文件是总纲，冲突时按「本文件 > `dev-docs/铁律.md` > `dev-docs/Agent协作体系.md` > 各角色卡」裁决。

---

## 一、核心原则

架构优先、设计优先、真源优先、严格验收。

- 编码前先想清楚：为什么做、是否正确、是否有更简单且更符合当前系统的做法。
- agent 必须敢于指出不合理需求、错误架构方向、冲突规则、缺失验收条件，帮助完善系统，而非机械执行。
- 禁止补丁式开发：不得用散落 if、临时兼容分支、硬编码、sleep、全局 flag、prompt 文案、mock/假数据绕过架构问题。
- 禁止无意义向后/向下兼容：旧字段、旧接口、旧产品残影若污染当前合同，先说明取舍，不擅自保留双路径。
- 禁止选项剧场：用户要求架构/方案时给一个推荐主线；备选只用于解释为什么不选。
- 禁止偷懒、糊弄、留尾巴。完成定义必须包含可验证结果、未闭合风险、下一步边界。
- 用户明确否定的概念必须从代码、文档、计划、命名中删除，禁止换名保留。
- 用户说"先看/不动代码/先给判断"时，保持只读审查，直到明确要求执行。
- **最小改动不是半截改动**：修 bug 不顺手重构、加功能不扩散清理；但本轮触达的调用链必须闭合到 owner、测试与文档。

## 二、项目边界（@@BOUNDARY@@）

- **做什么（goal）**：商家成长任务体系（京东拍拍二手·商家任务体系）。
- **三端**：商家端 H5（**主线**，PC Web 与移动端**同等重要**）、管理后台（适配 **PC Web 端**，Vue3 + Element Plus）、后端（Python FastAPI，`api-py/`；原 NestJS `backend/` 已作废）、数据库（MySQL 8.0）。
- **平台/运行面边界**：商家端横跨移动端与 PC Web，需同时覆盖两种视口与交互约束；管理后台仅面向 PC Web。
- **非目标/已否定**：无原生 App（仅 H5/Web 适配）；不引入第二个组件库；不偏离 `project/docs/设计规范.md` 的设计 Token 体系；不推翻已确认的既有路线。

## 三、真源优先级

事实冲突时按以下顺序处理：

1. 当前源码、测试、脚本、生成合同、schema、运行日志、实机/用户侧证据、当前 git 状态。
2. 项目根 agent 宪法：本文件 `AGENTS.md`（及等价 `CLAUDE.md`/`GEMINI.md`/Cursor rules）。
3. 真源索引 `@@TRUTH@@`（见下）。
4. 当前 active 的 charter/architecture/contract/implementation plan/acceptance/readiness/verification/audit 文档。
5. 当前仍有效的 docs/README/issue/review/commit history。
6. archive 历史文档、旧会话、旧记忆——只作模式证据，不覆盖当前事实。

**真源索引（@@TRUTH@@）**：
- `project/docs/设计规范.md`（视觉/组件库/设计 Token）
- `project/docs/开发规则.md`（前端框架/目录/文件归属/组件复用/硬性禁令）
- `project/docs/后端技术方案.md`（后端**唯一真源**：API 边界、业务规则、目录规范、变更管理）
- `project/docs/任务管理后台开发标准.md`（管理后台）
- `project/docs/数据分析专区方案.md`、`project/docs/阶段二任务体系.md`、`project/docs/阶段隔离规则与阶段二任务清单.md`
- `docs/前后端对接方案.md`（根级；**派生视图（当前对接手册）**——接口/字段/错误码真源 = `project/docs/后端技术方案.md`，两者不一致时以后者为准并回头修本文件）
- `dev-docs/Agent协作体系.md`、`dev-docs/铁律.md`、`dev-docs/子Agent线程登记.md`、`dev-docs/部署规则.md`（生产部署确认闸，独立成文）
- `dev-docs/planning/`（总控专用，子 Agent 禁读）
- `project/01-立项文档.md`、`project/02-规划说明.md`、`project/03-长期路线.md`

真源缺失、互相矛盾或技术上明显错误时，先报告冲突、证据与推荐处理方式，再等用户确认。

## 四、必需工作流

对立项/接管/功能/重构/修 bug/发布/文档任务，默认遵循：

`当前真源审计 → 推理闸 → 唯一 owner 与合同设计 → 测试/fixture/门禁计划 → 核心实现 → 薄 adapter/UI/CLI/API 接线 → 针对性验收 → 文档回写 → git 边界复核`

- **空项目启动**：禁止直接写码或选框架；先完成产品定义、唯一主线、第一闭环、技术栈确认与验收标准。
- **半路接管**：禁止当空项目重写；先做只读接管审计，确认既有代码、入口、调用链、接口契约、生成规则、测试脚本、配置、部署习惯、未提交变更与文档线索。
- **契约/生成物**：从合同、schema、manifest、SPI、service 或核心模型开始，而不是从 UI/HTTP handler/CLI/prompt/脚本倒推核心。

## 五、推理闸（编码前必答，未闭合不实现）

1. 实际要解决的问题是什么？
2. 谁创建这个概念、谁调用、谁消费？
3. 当前真源在哪？是否已有同职责模块/合同/schema/repository/service/状态机/文档？
4. **唯一 owner** 是哪一层或模块？哪些层禁止成为 owner？
5. 是否跨 UI/API/SDK/runtime/CLI/worker 多个入口？跨入口语义必须先进入共享合同或核心层。
6. 更简单、更保守的设计是什么？为什么不够？
7. 最大回归风险是什么？用什么测试/日志/命令/截图/实机证据阻断？

## 六、设计规则

- 共享语义必须单一真源：跨入口复用概念进入 `@@OWNER@@`，不散落在 adapter/controller/UI/prompt/脚本。
- adapter/controller/UI/CLI/HTTP/MCP/WSS/worker 只做协议映射、展示与接线，不拥有核心业务语义。
- 每个阶段必须有目的、收益、边界、验收命令与停止条件。
- 不为速度删除对账、身份、权限、审计、验证、实机证据、用户可见状态、数据完整性字段。
- 已有系统风格/组件/目录/命名/状态管理/错误处理时优先复用；仅在现有模式错误或不足时才提替换方案。
- 抽象只在能减少真实复杂度、定义必要边界、匹配已有模式时引入；禁止为"看起来架构化"过度封装。
- 修复若牺牲 UX/可见性/数据完整性/安全/硬件稳定性/产品边界，必须先讨论取舍。
- UI/renderer/页面/host/adapter/协议层只能消费 owner 提供的结构化状态、文案、projection、命令与错误原因；禁止私造业务真相、状态机、任务结论、权限结论、用户语义。
- 生成物只读不手改：发现 DO NOT EDIT、生成目录、schema/codegen 输出、bundle artifact、迁移生成物时，改源并重新生成。
- 所有外部输入/队列/缓存/请求体/响应体/会话窗口/文件大小/重试/超时/后台 worker 都要有上界、背压、释放或降级策略；禁止无界增长与永久常驻隐性运行面。

## 七、技术栈与适配块（@@STACK@@ / @@ADAPTER@@）

**通用适配规则**（仅当项目实际采用对应技术时启用；不适用则删，勿留空口号）：

- **FRAMEWORK**：商家端 uni-app + Vue3 + TS + SCSS + uview-plus + Pinia；管理后台 Vue3 + Element Plus + Pinia + axios + vue-tsc；后端 Python 3.12 + FastAPI + SQLAlchemy 2.0（同步）+ PyMySQL（`api-py/`；NestJS 已作废，禁止再改 `backend/`）。遵循各自生命周期、目录约定、状态管理、错误处理、测试与构建方式，禁止用框架后再私造一套并行体系。
- **LANGUAGE**：商家端/管理后台统一 TypeScript；后端 Python 3.12（类型注解 + Pydantic v2 校验）；代码风格、类型系统、包管理、lint/format 符合各端生态与既有规范。
- **UI**：商家端只用 uview-plus + 设计 Token；管理后台只用 Element Plus + 对应 Token；禁止引入第二个组件库。
- **DATA**：MySQL 8.0（api-py 不使用 Redis，Redis 非当前依赖）；schema/迁移/索引/事务/权限/缓存/连接池以 `project/docs/后端技术方案.md` = 数据层真源为准，表结构真源为 `project/scripts/schema.sql`；禁止业务层伪造数据合同。
- **AUTH**：鉴权/授权在服务端边界（FastAPI 依赖注入 + JWT，商家 token 与 admin token **双 secret**；见后端技术方案）执行；不依赖前端/页面/路由/中间件状态。
- **PERFORMANCE**：先定位真实瓶颈；独立 I/O 并行、重复查询去重、重计算缓存或下沉，不牺牲正确性与权限边界。
- **RESOURCE**：明确预算、上界、背压、超时、重试、熔断、idle-stop 与观测口径；保护机制介入不等于稳态通过。
- **PLATFORM**：商家端 H5 横跨移动端 + PC Web；管理后台仅 PC Web。低配平台裁剪不得污染高配能力，高配能力也不默认塞进受限平台。
- **DEPLOY**：前端两端（商家端 H5 / 管理后台）产物用 `npm run build` 生成；后端为 Python 服务（uvicorn，端口 8000，**未启用 --reload**，代码变更后须手动重启）；`project/serve.js`（端口 5173）静态服务；部署方案见 `dev-docs/部署方案-阿里云轻量1gib.md`（api-py 路线唯一标准）、`dev-docs/部署上线前必做清单.md`；禁止手改生成物。
- **TEST**：后端有 pytest 用例（`api-py/tests/`，运行 `uv run python -m pytest tests/ -q` 或 `api-py\.venv\Scripts\python.exe -m pytest tests/ -q`）；前端两端无自动化测试；核心合同用接口/契约验收、跨端用回归、UI 用截图/实机验收——由测试 Agent 承载，风险面匹配（见 `dev-docs/agents/测试Agent.md`）。

**适配块（@@ADAPTER@@）**：本项目实际采用的技术，按以下格式启用，不提升为通用宪法正文：
`framework/fastapi`、`framework/uni-app`、`framework/vue3-element-plus`、`orm/sqlalchemy`、`database/mysql`、`language-runtime/python`（Python 3.12）、`language-runtime/nodejs`（Node 20 LTS，前端工具链）、`toolchain/uv`、`toolchain/npm`、`toolchain/vite/uni-build`、`platform/alicloud`（轻量 1GiB）、`design-system/uview-plus`（商家端）、`design-system/element-plus`（管理后台）。
进入某适配块前先确认项目确实用该技术，只加载任务需要的适配内容。

## 八、默认命令（@@COMMAND@@）

统一验收入口在项目根执行：

- 硬门禁（无运行时可跑）：`npm run verify`（= 后端 api-py 校验 → 管理后台 build → 商家端 build:h5 → 数据库门禁（结构 / 数据编码 / merchant_id 孤儿）→ **pytest 全量套件**；具体脚本以根 `package.json` 为准）。⚠️ 全链约 **6 分钟**（含两端构建与 pytest ≈3 分钟）；**pytest 自 2026-09-15（`#OPS-38`，用户裁决 D3）起纳入本链**，3 条 xfailed 属已登记的例外（见 `dev-docs/planning/progress.md` §60 D1）
- 冒烟探活（需运行环境，探全流程可达）：`npm run verify:smoke`（按 `project/serve.js` 端口 5173 与后端端口 8000 实际监听探活；接口级探活由测试 Agent 专项验收承担）
- 商家端：`npm run dev:h5` / `build:h5`；管理后台：`npm run dev` / `build`
- 后端（`api-py/`）：启动 `uv run uvicorn app.main:app --host 127.0.0.1 --port 8000`；测试 `uv run python -m pytest tests/ -q`（备选 `api-py\.venv\Scripts\python.exe -m pytest tests/ -q`）；数据库结构校验 `uv run alembic current`（Alembic 只校验结构、不 alter 生产表）；**未启用 --reload**，代码变更后须手动重启。注：优先用 `uv run`——Windows cmd 下 `.venv/Scripts/python.exe` 正斜杠形式不可执行（2026-09-10 实测）
- 部署/预览：`node project/serve.js`（5173）；后端健康 `GET /health`；API 文档 `GET /docs`（仅 DEBUG=true 可访问，生产 404）

## 十、实现规则

- 添加测试/fixture/gate 脚本时，放在风险真正所属的层级。
- 用结构化 API、解析器、生成器、本地 helper，不用脆弱字符串拼接与临时路径判断。
- 不手改生成文件；有生成器则运行生成器并检查输出。
- 不用旧记忆、旧输出、"应该是这样"代替当前命令与当前代码证据。
- 修改代码/接口/配置/架构边界/用户行为/产品语义后，必须同步项目文档。
- 收到 review 反馈或用户质疑时，先查当前实现、框架底层、可复现证据，再决定是否接受修改。
- 修改 agent 行为规则/宪法/skill/系统提示/workflow 模板前，说明现有规则为何不够、影响哪些行为，并用 ≥1 个真实场景或压力测试验证有效。
- 生产路径用统一错误类型、结构化错误、stage/context 返回失败；禁止 panic/unwrap()/expect()/裸异常/固定字符串/静默吞错处理可恢复问题。
- 配置/密钥/权限显式下传或走项目既有配置系统；禁止全局可变静态、硬编码密钥、日志明文敏感信息、把安全字段写入普通 artifact。
- 观测/指标/健康/资源快照/诊断来自真实数据源；拿不到就返回 N/A、空集合或结构化不可用原因，禁止固定值/占位值/伪健康状态。
- 用户可见文案/错误提示/按钮/空态/报告标题/技能说明遵守项目 i18n/文案真源；禁止临时硬编码自然语言后续再补。

## 十一、多 Agent 规则

- 优先多 agent 执行，但只在任务能拆成互不干扰的独立域时用。
- 每个子 agent 有明确范围、输入、禁止事项、期望输出。
- 不把当前关键路径阻塞任务丢给子 agent 后原地等待；主 agent 继续做不重叠工作。
- 多 agent 改码分配不重叠文件/模块 owner，集成时复核冲突。
- 子 agent 结论非最终真源；最终结论由主 agent 对照当前代码、测试、文档验收。
- 细则见 `dev-docs/铁律.md`、`dev-docs/Agent协作体系.md`；子 agent 禁读 `dev-docs/planning/`。

---

## 十二、验收规则

- 验收必须匹配改动风险，不只跑最轻命令就宣布完成。
- 声称"完成/修好/通过"前，提供本轮实际跑过的命令、测试、日志、截图、构建、设备或用户侧证据。
- 无法跑某项关键验收，说明原因、影响范围、可替代证据，不隐瞒。
- 发现失败先复现、收集证据、建立可证伪假设，再修改；禁止无复现地猜原因。
- UI/前端改动必须检查真实渲染、交互、加载态、错误态与移动/桌面约束，不得只看代码。
- 性能/安全/数据/权限/并发/迁移/发布相关改动必须扩大验收面。
- warning/lint/类型告警、格式漂移、生成物漂移、文档索引缺失、本轮 TODO/TBD 按缺陷处理；除非明确记录为非本轮债务，否则不能带着它们声称完成。
- 测试若依赖隔离状态，必须显式构造隔离边界；基于缓存/最近窗口/截断列表/有限快照的测试不能伪装成全局累计事实。

## 十三、文档分层

- 写文档前先判断受众：内部真源、外部用户、发布说明、技能文档、审计记录、一次性复盘不混写。
- 内部架构/agent 宪法/owner map/验收门禁/治理历史/审计结论/阶段计划/漂移控制 → 进 `@@TRUTH@@`（含 `dev-docs/planning/`、`dev-docs/agents/`）。
- 外部用户文档只写使用、部署、配置、公开 API、集成、硬件接线、运维、排障（如 `dev-docs/部署方案-阿里云轻量1gib.md`）。
- 同一变更同时影响用户行为与内部机制时，分别写入对应层。
- 新增当前真源文档必须被真源索引引用；完成/失效/被吸收/一次性的文档归档或标注非当前，不留在主目录误导后续 agent。

## 十四、Git 规则

- 提交/发布前确认 git root、`git status --short`、ignored 文件、staged file list、嵌套仓库边界。
- 禁止 `git add .`；只 stage 与本任务相关文件。
- 禁止 force-add ignored 文件，除非用户明确点名路径并要求。
- dirty worktree 中不得回滚、覆盖、吸入用户未授权改动。
- 若有嵌套仓库，父/子仓分别审计、验收、staged、提交。
- 不用破坏性 git 命令，除非用户明确要求并确认风险。
- **Git 提交（commit/push）必须由用户本轮明确指示**；测试通过/建议可提交 ≠ 自动授权提交（见 `dev-docs/铁律.md` 铁律 1.5）。

**生产部署确认闸（2026-09-14 用户确认规则）**：未获用户在本轮明确确认前，变更**只能在开发环境供人眼预览**，确认后才构建、部署、上线。

- 完整规则见 **`dev-docs/部署规则.md`**（独立成文，**不在铁律内**；涉及代码/配置/数据改动、以及 compact 后恢复工作时必读）。
- 一句话边界：未确认前禁止上传/替换生产目录、执行生产 DDL/DML、改生产配置、重启生产服务；自测通过、门禁 PASS、构建成功**都不等于**用户确认。

## 十五、对外贡献规则

- 对外 PR/patch/issue/发布前，先读仓库贡献规则、PR 模板、已 open/closed PR、issue、维护者反馈。
- 确认是用户真实遇到、当前代码可复现的问题；禁止理论审查、猜测、编造问题发起贡献。
- 一次只解决一个问题；禁止混入无关改动、顺手重构、格式化风暴、项目私货。
- 只服务某团队/领域/工具/fork/个人习惯的改动放插件/扩展/配置/项目私有层，不塞通用核心。
- 提交前说明完整 diff 范围、验证证据、剩余风险，获明确确认后再发布。

## 十六、必须停止并询问

1. 用户需求、当前代码、agent 宪法、真源文档、验收结果互相冲突。
2. 需无意义兼容、保留旧产品残影、同时支持互斥路线。
3. 需创建/改写/废弃 agent 宪法、真源索引、公开文档、产品命名、核心 API、schema、权限模型、部署流程。
4. 需删除旧 API/字段/路由/配置/缓存/生成合同/部署脚本/迁移历史。
5. 当前证据表明用户目标会损害架构、数据、安全、权限、UX、长期可维护性。
6. 上下文不足判断 owner 边界，且猜测会致不可逆或大范围影响。
7. 需把尚未经用户人眼确认的变更部署到生产环境（见 §十四「生产部署确认闸」）。

停止时不要只说"无法继续"，必须给出：冲突证据、可选处理方向、推荐方向、需用户确认的问题。

## 十七、交接规则

上下文过大/换窗口/换 agent/任务未闭合时，产出可直接复制的交接文本，包含：

- 当前目标与已确认的产品/架构边界。
- 当前 git 状态、已改文件、未提交文件、嵌套仓库状态。
- 已完成工作、实际验收命令与结果。
- 未闭合风险、漂移警告、禁止触碰的用户改动。
- 下一步最安全命令与停止条件。

**常态化更新（2026-09-10 用户确认规则）**：长期交接载体为 `dev-docs/迁移交接-2026.md`，**项目每发生较大变化（真源/架构/服务基线/关键完成项/待裁决项变动）即须同步更新**，不得只在换窗口时才补写。

**上下文压缩/换窗口后的时效校验（2026-09-10 用户确认规则）**：恢复工作前须核对交接文档与当前事实是否一致——判据以**当前源码/文件 mtime/进程创建时间/实测命令输出**为准，**不得采信任何「我的代码没加载/没改」一类自述**；发现不一致即视为缺陷，先修正交接文档再继续。

**compact / 换窗口后的必重读范围（2026-09-14 用户扩围）**：**先把项目内的「铁律 + 规范 + 规则 + 真源」完整重读一遍再动代码/派单**；完整清单（A 规则与协作类 8 份 + B 项目真源 9 项 + C 角色卡 + D 本轮任务上下文）见 `dev-docs/铁律.md` **铁律 3.1**，最短入口见 `dev-docs/迁移交接-2026.md` §〇。重读后须在当轮逐条列出「已重读」清单。

## 二十、工作流程

1. 接到开发任务。
2. **读 `project/docs/设计规范.md`** → 确认样式取值。
3. **读 `project/docs/开发规则.md`** → 确认文件位置、是否需封装组件。
4. **读 `project/docs/后端技术方案.md`** → 确认 API 规范、业务规则、数据库交互。
5. 按规则执行开发（涉及接口读 `project/docs/后端技术方案.md` 接口真源；`docs/前后端对接方案.md` 为**派生视图**，冲突时以后端技术方案为准并回头修本文件）。
6. 完成后自查：文件归位？样式取自 Token？重复 UI 已封装？API 符合后端技术方案？是否引入第二个组件库？是否含未闭合 TODO/警告？
