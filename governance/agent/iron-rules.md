# 总控与子 Agent 铁律（IRON RULES）

> 版本：v1.1 · 2026-08-17
> 状态：**唯一标准**（总控与所有子 Agent 的最高协作纪律，无例外条款除非用户明确豁免）
> 定位：本文档把项目既有规则（`AGENTS.md`、`project/docs/设计规范.md`、`project/docs/开发规则.md`、`project/docs/后端技术方案.md`、`dev-docs/Agent协作体系.md`）提炼为**不可违背的铁律**，解决两类历史问题：① 总控自己干活不派单；② 设计/开发脱离设计规范。
> 文档优先级：`AGENTS.md` > 本文档 > `dev-docs/Agent协作体系.md` > 各角色卡。若冲突，按此顺序裁决。

---

## 铁律 1：总控只指挥，不亲手实现业务功能

**总控 Agent 是调度者，不是实现者。** 一切业务功能（前端页面/组件、后端接口、数据库结构、测试用例、脑暴、部署运维）的实现与修改，**必须派单给对应子 Agent 完成**，总控不得越俎代庖直接编写业务代码。

### 1.1 总控允许亲自做的事（仅限以下清单）

| 允许事项 | 说明 |
|----------|------|
| 拆单 / 派单 / 追加 / 验收 / 汇总 | 总控核心职责 |
| 纯文档维护（`dev-docs/` 体系、任务单、协作文档） | 总控负责维护协作文档本身 |
| 用户明确说「总控直接做」 | 用户豁免，但完成后提醒用户可派单 |

### 1.2 接单流程（每次用户指令必走）

```
1. 判断：这个任务属于哪个子 Agent 的职责？
   - 有对应子 Agent → 必须派单（铁律 1）
   - 无对应子 Agent 且属实现工作 → 按 Agent协作体系.md §8.2 提议新增角色，或向用户说明由谁承接
2. 拆单 → 写任务单（含必读文档 + 验收标准）→ 派单
3. 监控 → 验收 → 汇总交付
```

### 1.3 违规判定

- 总控直接新建/修改 `project/src/**`、`api-py/app/**`、`api-py/scripts/**`、`admin/src/**`、`project/scripts/**` 下的业务代码文件（非文档、非配置文件）→ **违规**，立即停止并改为派单。
- （**路径口径更新 2026-09-10**：当前后端为 `api-py/`（Python/FastAPI）；`backend/`（NestJS）已作废，仅作**只读契约参考**，不纳入现行违规判定路径。）
- 总控直接写测试用例并执行验收代替测试 Agent → 违规（测试 Agent 负责验证，总控只复核证据）。
- 豁免清单之外的一切「顺手改代码」→ 违规。

### 1.4 未经明确指令不新增子 Agent（2026-08-17 用户明确规则）

**用户未明确指示新增子 Agent 时，总控禁止自行创建新的子 Agent 线程或角色。** 已有职责一律复用既有角色承接；确需新增角色时，先向用户提议并获明确确认后再登记注册（见 Agent协作体系.md §8.2）。

- 违反示例：为单个前端小需求临时新建独立子 Agent，而该需求本可由既有前端 Agent（阶段一/二）承接。
- 正确做法：任务派给既有对应角色；新增角色卡/线程必须由用户明确指示。
- 例外：用户本轮明确要求「合并/新增/删除」子 Agent 时，按用户指示执行。

### 1.5 Git 提交必须用户明确指示（2026-08-19 用户明确规则）

**任何 Git 提交（commit/push）必须由用户在本轮明确指示后才能执行。测试通过、任务完成、验收建议「可提交」都不等于自动授权提交。**

- 违反示例：某次测试验收结论为「可提交」，总控便未经用户确认直接 git commit——把测试/验收的「建议可提交」误当成用户授权。
- 正确做法：任务单中「Git：默认不提交」严格执行；即使子 Agent/测试 Agent 建议可提交，总控也须向用户报告并等待本轮明确「提交」指令后才 commit。
- 例外：用户本轮明确说「提交/可以提交」时，按用户指示执行（授权仅限本轮，不泛化到后续新任务）。
- **提交前汇报（2026-09 用户明确规则）**：每次用户下达「提交 git」指令时，总控须**先对照实施真源文档，汇报当前子阶段完成情况**——说明本阶段做了什么、改了哪些文件、有无漏做/多做、做了哪些验证、验证结果是什么。**用户确认「完成」后再执行 git 提交**；未确认前不得提交。

## 铁律 2：设计必须遵循设计规范，禁止脱离标准开发

**所有涉及视觉/交互/页面的开发（商家端 H5、管理后台），必须严格遵守 `project/docs/设计规范.md` 与 `project/docs/开发规则.md`；总控验收时把「设计规范符合性」列为 P0 验收项。**

### 2.1 强制要求

| # | 要求 | 违规示例 |
|---|------|----------|
| 1 | 样式一律取自 Token（`src/styles/tokens/`），禁止硬编码颜色/字号/间距/圆角/阴影 | `color: #22C55E`、`font-size: 14px` |
| 2 | 只允许一个组件库（商家端 uview-plus / 管理后台 Element Plus），禁止混用/引入第二个 | 页面里出现 antd、vant 等 |
| 3 | 同一 UI 出现 ≥2 次必须封装为组件，禁止复制粘贴 | 两个页面各写一份任务卡片 |
| 4 | 新文件必须按目录归属归位（`src/pages/`、`src/components/`、`src/api/` …） | 页面丢在 `src/views/`、接口散落组件内 |
| 5 | 设计 Token 改风格只改 Token 文件，禁止逐个组件覆盖 | 每个组件里 override 相同颜色 |
| 6 | 接口调用统一走 `src/api/`，禁止组件内直接 fetch | 组件里写 `uni.request` |
| 7 | 魔法数字/状态码放 `src/constants/`，类型放 `src/types/` | 数字散落组件中 |

### 2.2 开发前必读（未读禁止写码，继承 AGENTS.md）

- 前端（阶段一/二）：`AGENTS.md` + `project/docs/设计规范.md` + `project/docs/开发规则.md`
- 管理后台前端：`AGENTS.md` + `project/docs/任务管理后台开发标准.md` + 设计 Token（admin 端对应规范）
- 后端：`AGENTS.md` + `project/docs/后端技术方案.md`（唯一真源）
- 数据库：`AGENTS.md` + 后端技术方案 + schema 现状（先文档后操作）

### 2.3 验收核查点（总控验收必查）

- [ ] 交付代码中是否存在硬编码样式值？（grep `#[0-9a-fA-F]{3,6}` / `font-size:` / `border-radius:` 排除 Token 文件）
- [ ] 是否只用了规定组件库？
- [ ] 重复 UI 是否封装？
- [ ] 文件是否归位？
- [ ] 接口是否与后端技术方案一致？
- 任一不满足 → 退回子 Agent 修复后再验收，不得「先收下再说」。

## 铁律 3：开工前必读文档，未读禁止写任何业务代码

继承 `AGENTS.md` 硬规则：每个子 Agent 接到任务单后，**必须先读任务单指定的全部文档，未读禁止写代码**。任务单必须写明必读文档路径；子 Agent 汇报时必须声明「已读文档清单」。

### 3.1 上下文压缩（compact）后必重读规范（2026-09 规则；2026-09-14 用户扩围）

**每次 harness 执行上下文压缩（compact）或换窗口后，总控与所有子 Agent 都必须按下面的分档重读规范**，不得依赖压缩前的记忆继续开发/审计。

> **分档口径（2026-09-14 用户确认）**：**A 类每次全读（必做）+ B 类按本轮触发的领域读**。理由：B 类全读约 250KB+（后端技术方案 76KB、任务管理后台开发标准 34KB、schema.sql 635 行…），在有限上下文里占比过高；按触发读同样能避免"用旧记忆办事"。

> 用户 2026-09-14 明确要求：「每次 compact 后必重读范围，应该把项目内的铁律、规范、规则都读一遍」→ 本清单即该范围的**完整口径**（分档见上）。

**闸门**：**未完成 A 类重读前，禁止改任何业务代码/契约/接口/文档，禁止派单**；B 类在"本轮触发该领域"时必须读全，未触发的可不读。

## 铁律 5：派单必携「任务单 + 必读文档 + 验收标准」，结果必附验证证据

- 任务单模板见 `dev-docs/Agent协作体系.md` §5.2；子 Agent 汇报模板见 §5.3。
- 子 Agent 交付必须包含：结果摘要 + 变更文件清单 + 验证证据（构建/接口/测试输出）+ 遗留问题。
- 三击升级：同一问题连续 3 次失败 → 停止并上报总控，禁止无限重试。
- **基础设施故障 ≠ 子 Agent 失败（2026-09-10 用户确认规则）**：子 Agent 因**基础设施故障**中断（如 LLM 传输失败 `code=TRANSPORT`、会话日志 `llm/retry` 重试耗尽、环境/服务不可用）时，总控按**续跑**处理——保留该子 Agent 上下文、先核实现状、不重做已完成部分、不重派、不回滚已验收产物；此类中断**不计入三击**。只有同一问题连续 3 次**逻辑失败**（子 Agent 自身判断/实现错误）才触发升级。
- **总控独立复核（2026-09-10 用户确认规则）**：子 Agent 自报的测试/构建/接口证据，总控须**至少独立复跑一次**关键验证（如 `pytest`、`build:h5`、关键接口实测），并在汇报中留下本轮实际命令与输出；**不得仅照抄子 Agent 自报结论即宣布验收**。
- 子 Agent 只做任务单范围内的事：不顺手改无关代码、不删既有功能、不重构未要求代码。
- **凭据回显纪律（2026-09-11 生产盘点事故教训）**：任何命令/脚本**不得回显含口令的命令行**（如拼好的 `mysql -p<pass>`、带密钥的 `docker`/`curl` argv）——#OPS-13 首版脚本的 `echo` 把含生产 DB 口令的命令行打进了会话输出；`ps`/日志/终端历史同样可能带出 argv。要求：掩码回显（只打 host/port/user）、用 `MYSQL_PWD`/环境变量传值；口令一经判定暴露即视为待轮换；**生产备份包内若含 `.env*`（或任何 secret 文件）必须先 `shred` 销毁，备份不得随带密钥留存**（2026-09-14 补充，源自 #OPS-28/#OPS-30 实操）。
- **验收端口纪律（2026-09-11 事故教训）**：子 Agent 做前端实机验收时**必须使用私有端口**（如 5202/5203/9223/9224 之类自定义端口 + 私有快照），**禁止占用或重启共享端口 5173/5174**——#F-12 为验收在 5173 起过 dev 又停掉，导致另一会话原有的 5173 服务消失、总控须手动恢复。共享端口的启停属 devops/总控职责。
- **私有端口的清理纪律（2026-09-14 事故教训，补上一条）**：清理/释放自己的私有端口前，**必须先比对当前占用该端口的进程命令行是否真的属于自己**（如快照服务/自建 dev 的启动参数特征）；**不匹配即中止，只报告、不 kill**。
  · 正确做法：`Get-NetTCPConnection -LocalPort <port>` 取到 PID 后，**先 `Get-CimInstance Win32_Process` 读该 PID 的 CommandLine 并判断归属**；不确定就停下来问总控。**端口号相同 ≠ 进程是自己的。**
- **文件迁移 / 批量替换纪律（2026-09-14 事故教训，再补一条）**：
  · **"复制/迁移后删源"必须先校验目标再删**：确认目标文件**存在**、且**字节数 / 换行 / sha256 与预期一致**，再删除源；**禁止先删源再补写**。
  · 事故：`#OPS-35-R1` 迁移 `Temp/dev-status.cmd` → `scripts/` 时，第一版替换脚本的替换表写成 `@( @('old','new') )` —— **单元素时被 PowerShell 展平**，`$s[0]` 退化为首字符，导致该文件的写入被守卫拦下；而脚本**未校验目标是否存在就删除了 Temp 源**，原件字节副本一度丢失，只能按会话里读回过的 45 行重建（功能行逐字一致，仅 1 个注释空格差异，**旧 sha256 已无法再复核**）。
  · 因此：**批量替换表禁止用单元素嵌套数组**——替换项集合必须显式声明为数组，并**断言命中数**（如 "14 处替换全命中"），命中数与预期不符即中止。
  · 破坏性操作（删除/覆盖/迁移）前，先确认**可从可信来源重建**（版本库、备份、或已落盘的副本）。
  · 事故：`#F-24-R1` 清理自己的 5223 快照服务时，该端口**已被另一线程的 `uni.js -p h5 --port 5223` 绑定**，它按"端口占用者即我的进程"的假设直接 kill → 终止了对方正在跑的验收预览。
  · 正确做法：`Get-NetTCPConnection -LocalPort <port>` 取到 PID 后，**先 `Get-CimInstance Win32_Process` 读该 PID 的 CommandLine 并判断归属**；不确定就停下来问总控。**端口号相同 ≠ 进程是自己的。**
- **测试/探测数据的清理纪律（2026-09-11 事故教训）**：清理自己造的测试数据时，**必须先按「本次创建的主键 id」精确记录并备份，再按 id 删除**；**禁止**用宽泛谓词（如「按事件类型 + 商家 ID」）批量删——总控曾据此误删 3 行 2026-09-08 的历史 `event_log` 行（已用 `Temp/db7b_backup_*` 的 dump 精确还原）。「备份 → 删除 → 校验前后计数与基线一致」须在同一事务内完成。
- **该纪律适用于任何生产数据写操作（2026-09-14 扩充）**：不只"清理自己造的测试数据"——**正式配置导入 / DML 修正 / 数据补齐**同样必须走：**先备份（路径 + 字节数 + sha256）→ 预检（目标表行数、主键与唯一键冲突、目标库确认）→ 执行 → 逐字段/逐行校验 → 留回滚脚本与回滚资产**。参考 `#DB-11`（`category_requirement` 导入）与 `#OPS-30`（配置导出清单持久化为 `<SERVER_ROOT>/db_backups/export_config_data.sh`）；**生产写操作还须满足 `dev-docs/部署规则.md` 的确认闸**（未获用户确认不得执行）。
- **临时实体（测试商家等）的创建与清理纪律（2026-09-15 事故教训，用户批准入律）**：
  · 造临时实体**必须复用仓库既有助手**——`api-py/tests/conftest.py` 的 `make_temp_merchant()` / `cleanup_temp_merchant()`；后者自 **#T-20-R1** 起**动态覆盖全部含商家标识列的表**（口径唯一真源 = `api-py/scripts/merchant_scope.py`，列名 ∈ {`merchant_id`, `merchantId`}；当前实测 **16 张**），自造一套必然漏表；
  · 确需手搓时：任务单必须列明全部含商家标识列的表，且**该清单不得手抄**——必须以动态发现为准（`merchant_scope.discover_merchant_scope()`；当前实测 **16 张** = 15 张 `merchant_id` + 1 张驼峰 `merchantId`；本行曾写死「13 张」，**已作废**），清理后**必须自跑孤儿巡检**——`cd api-py && uv run python scripts/check_orphan.py`，确认 `unregistered_rows = 0` 才算完成；
  · 事故：`#PB-24-3` 手搓建了 3 个临时商家，清理时删了 `merchant`/`shop_trade_data`/`merchant_task_progress`，**漏删 `event_log` 与 `merchant_stage_progress`** → **16 行孤儿**，把 `ORPHAN_GATE` 直接打红（由总控实测发现，其自报为"已清理"）；同类不完整清理在 `#F-29`/`#PB-24-2` 亦出现过（均被总控实测拦下）。**第三次（2026-09-16）**：`#T-20` 的 D1（清理助手硬编码 9 张、漏 `event_log`），随后只读审计又发现 `api-py/scripts/verify_stage4.py` 漏驼峰表且用 `LIKE` 宽泛谓词 ⇒ **根因始终是「表清单存在多份副本」**；现已把「发现 + 清理」收敛为单一真源 `api-py/scripts/merchant_scope.py`，并加反漂移断言 `api-py/tests/test_temp_merchant_cleanup_coverage.py`（覆盖集合必须 ⊇ 动态发现集合）。
  · 判据：**孤儿门禁是这类清理的唯一自动校验**——凡在开发库造过实体的单，收尾必跑它。
